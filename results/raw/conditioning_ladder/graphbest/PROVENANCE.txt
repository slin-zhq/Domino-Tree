BUILDER CONFIGURATION (this is what differs from conditioning_ladder_20260816/)
  marg@16        Python. Nothing to graph: its children fn returns precomputed
                 per-depth menus, so per-node work is ~free and its cost is the
                 (inherently un-graphable) Python best-first heap loop.
  condstatic@16  CUDA-graph captured (domino_adapter.GraphStaticCorrector). Its whole
                 D=16 greedy trajectory is a fixed sequence over fixed shapes, so it
                 captures as ONE graph, replayed once per round.
  dominotree@16  CUDA-graph captured per node (dominotree_gpu.GraphNodeExpander).
                 Best-first pop order is data-dependent, so only the per-node
                 correction can be captured; it replays 15x per round.

HOW TO READ THE TWO CONFIGURATIONS
  The matched run isolates the SCORING FUNCTION by holding construction cost fixed;
  it is the ablation proper (path-dependence = +4.05%). This run shows what a deployer
  gets with each arm at its best (+12.56% total over a marginal tree). The split moves
  between them because graph capture helps condstatic more than DominoTree -- a
  path-INDEPENDENT trajectory captures as one graph, while best-first's data-dependent
  pop order forces one replay per node. Neither configuration is the "true" one; they
  answer different questions and the paper reports both.
